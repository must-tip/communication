# MustTip Communication SDK

`musttip-communication` is the shared durable communication layer for MustTip Django services. Kafka is the canonical production transport for the current platform; NATS compatibility remains optional so existing public APIs are not broken.

## Runtime contract

The SDK matches the Kafka workload contract generated by `cloud-services`:

```text
KAFKA_BOOTSTRAP_SERVERS=kafka-bootstrap.kafka-system.svc.cluster.local:9092
KAFKA_SECURITY_PROTOCOL=SASL_SSL
KAFKA_SASL_MECHANISM=SCRAM-SHA-512
KAFKA_USERNAME or KAFKA_SASL_USERNAME
KAFKA_USERNAME_FILE=/var/run/secrets/kafka-client/username
KAFKA_PASSWORD_FILE=/var/run/secrets/kafka-client/password
KAFKA_CA_FILE or KAFKA_SSL_CA_LOCATION=/var/run/secrets/kafka/ca.crt
COMMUNICATION_ENABLED_TRANSPORTS=kafka
COMMUNICATION_CONSUMER_TRANSPORTS=kafka
COMMUNICATION_PRIMARY_TRANSPORT=kafka
```

Direct secrets and mounted Secret files are both supported for compatibility. Mounted files are preferred in deployed environments. Credentials are never included in redacted configuration output.

## Kafka invariants

The SDK enforces the platform design rather than trusting application overrides:

- `SASL_SSL`/SCRAM credentials when configured by the platform;
- CA verification and hostname verification;
- `acks=all` and idempotent producers;
- `max.in.flight.requests.per.connection=5`;
- automatic topic creation disabled for producers and consumers;
- manual offset commit after successful handling;
- `read_committed` consumption;
- bounded callback processing below `max.poll.interval.ms`;
- stable event IDs and database-backed outbox/inbox support.

Applications must use service-specific Kafka principals and least-privilege ACLs. Never use the Kafka `admin` principal from a microservice.

## Installation

Kafka-enabled services must install the Kafka extra explicitly:

```bash
pip install 'musttip-communication[kafka]==1.1.0'
```

The Python import path remains:

```python
from communication.config import CommunicationSettings
from communication.bus import EventBus
from communication.outbox import OutboxService
```

## Django integration

`CommunicationSettings.from_django_settings()` accepts the existing nested `COMMUNICATION`, `KAFKA`, and `KAFKA_CONSUMER` dictionaries and the platform aliases listed above. It also reads `KAFKA_USERNAME_FILE` and `KAFKA_PASSWORD_FILE` when Django exposes only mounted-secret paths.

For standalone SDK verification without Django:

```python
from communication.config import CommunicationSettings

settings = CommunicationSettings.from_environment()
```

## Real Kafka diagnostic

The package includes an operational diagnostic that verifies, in order:

1. runtime configuration and mounted files;
2. broker metadata reachability (DNS, TCP, TLS, SASL);
3. consumer startup;
4. producer acknowledgement;
5. actual reception of the exact test record by a unique consumer group.

A dedicated diagnostic topic must already exist. The SDK deliberately does **not** auto-create a topic and will not silently use a business topic.

Run directly against the same environment/Secret mounts provided by `cloud-services`:

```bash
export COMMUNICATION_KAFKA_TEST_TOPIC='<pre-provisioned-diagnostic-topic>'
export COMMUNICATION_KAFKA_TEST_GROUP_PREFIX='<service ACL group prefix>'
musttip-communication-kafka-check --source environment
```

Inside a Django service, this additionally validates that the service's Django settings map the injected values correctly:

```bash
export DJANGO_SETTINGS_MODULE=config.settings
musttip-communication-kafka-check --source django \
  --topic "$COMMUNICATION_KAFKA_TEST_TOPIC"
```

The command emits one JSON result. The `stage` field identifies where the failure occurred (`configuration`, `broker_metadata`, `subscription`, `publish_ack`, or `receive`) without printing credentials.

## Automated tests

Deterministic SDK suite:

```bash
pytest -q
```

Live broker round trip (explicit opt-in):

```bash
RUN_KAFKA_INTEGRATION=1 \
COMMUNICATION_KAFKA_TEST_TOPIC='<pre-provisioned-diagnostic-topic>' \
pytest -q -m integration tests/test_kafka_live.py
```

Run the live test inside a Kafka-enabled Kubernetes pod or a CI runner that has the same network path, CA and SCRAM secret mounts as the target service. If the SDK unit suite and standalone environment diagnostic pass but `--source django` fails, the defect is in the microservice's settings/integration layer rather than the Kafka transport.

## Delivery model

Direct publication is at-least-once. For business state changes requiring durable event publication, insert the SDK `OutboxEvent` in the same database transaction as the business change and drain it from a separate worker. Consumers must remain idempotent.

A Kafka acknowledgement timeout is treated as an **unknown publish outcome**, not proof of failure. Do not blindly generate a new logical event ID when retrying an outbox record.

## Operations

Readiness may depend on Kafka when Kafka is a required transport. Liveness must not fail solely because Kafka is temporarily unavailable. Monitor producer failures, consumer worker termination, commit/seek failures, DLQ volume, outbox age/retries, and consumer lag.

See `docs/` for architecture, testing, runbook, rollback, security controls and known gaps.
